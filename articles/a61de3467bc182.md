# はじめに

Claude Code や Cursor といった，Coding Agent ツールに思った通りのコードを書かせるために，ドキュメントやルールをせっせと生産する時代になったわけですが，ドキュメントが増えれば増えるほど，AI は正しいドキュメントを探すためにたくさんの Token を消費したり，それでいて適切な情報にたどり着けなかったりします．

# AI 駆動開発の現場では

最初は， `AGENTS.md` に簡単なディレクトリ構成などを書きます．
少しずつ固有の設計や実装ルールが増えてくると，`docs/architecture.md` に移して，設計方針をまとめます．
`AGENTS.md` には， 

```md
**実装するときには，必ず `docs/architecture.md` を参照し，ルールに則ること**
```

なんて書いてみたりします．

仕様も Markdown にし，リポジトリで管理しようということになり， `docs/specifications/*.md` が誕生します．
いろんな設計や仕様の議論も残しておきたいということになり， `docs/adr/*.md` が誕生します（ADR は Architecture Decision Record）．

こうやって，どんどんドキュメントが増えてきて，AI が読むコンテキストが膨大になります．

Read ツールを十数回コールしたり，grep でキーワード検索をしながらドキュメントを探すようになりますが，段々と適切なときに適切なだけドキュメントを読んでくれなくなり， 消費する Token ばかりが増えていきます．

ここで，ドキュメントを RAG に突っ込んで意味的な検査ができるようにすればいいじゃん！という話になり，そういう MCP ツールを探します．
僕も過去にこんな MCP ツールを作りました

https://github.com/fuwasegu/exocortex

# 第二の脳 Exocortex と RAG

Exocortex は人間の脳の記憶メカニズムを（素人なりに）できるだけ再現して，知識をネットワーク化し，グラフ検索とベクトル検索のハイブリッド方式で知識を保存，検索するツールです．いわゆる，RAG（Retrieval-Augumented Generation）と言われる技術を使った検索ツールです．

https://x.com/fuwasegu/status/1997957579406971306?s=20

https://x.com/fuwasegu/status/1999509262267973672?s=20

たしかにそれっぽいナレッジグラフが作られていって，検索もそこそこいい感じだったので，ついに LLM に長期記憶を与えることができた！という手応えがありました．

でも，実際開発で使ってみると，期待していた使い心地ではありませんでした．

例えば，「ブックマークの並べ替え機能を実装して」と Agent にお願いすると，「ブックマーク」「並べ替え」というキーワードでベクトル検索をかけます．
もちろん，そんなので引っかかる知識が適しているはずありません（過去に同様の機能を作ったことがあってそれが記憶されていれば，もしかしたら有益な知識を引っ張り出せた可能性はあります）．
本当にほしいのは，どういう粒度でドメインモデルを定義するかとか，UseCase にはどういう責務を追わせるべきなのかとか，プロジェクト固有の例外設計ルールはどう定義されているのかとか，そういう情報です．

つまり，「ブックマーク」という実装のキーワードと，「UseCase の責務」というアーキテクチャ規約の間には，セマンティック・ギャップがあるということです．

たまたま，AI の勘が冴えていて，「UseCase」「Collection」「Exception」「ドメインモデリング」のような，実装する上で必要そうな知識をあらかじめ検索してれていることも稀にありました．でも AI の気分で品質が左右するようでは，AI に実装を任せることなんてできません．

かと言って，都度，「今回の実装ではあれとこれとそのドキュメントを事前に参照してください」なんていちいち必要なドキュメントを人間が探してあげるのも手間です．

つまり，僕が求めているのは確率的なナレッジ検索やあいまいな連想ではなく，「決定的な知識の依存関係の解決」であると考えました．
そのために，僕は新たに Aegis という MCP ツールを開発しました．

https://github.com/fuwasegu/aegis

# DAG（有向非巡回グラフ）を使ったコンテキストのコンパイラ Aegis

最近の Coding Agent には Plan という機能があります．
与えられた要件をもとに，どういう実装をするかあらかじめ計画し，人間に確認を求めます．

このとき，どのようなパスに，どういうファイルを作るかも，ある程度計画されます．
例えば，`app/UseCases/` に UseCase を実装すると計画したとすると，僕が期待する Agent の動きは次のとおりです．

Agent「`app/UseCases/` に UseCase を実装するやで」
Agent「`app/UseCases/` になにかを実装するときは，`usecase_guidelines.md` を読むって決まっているんや」
Agent「`usecase_guidelines.md` を読むときは」
Agent「その前提となる `entity_guidelines.md` と `exception_guidelines.md` も読むんや」

このような芋づる式に必要なドキュメントを辿って取得する仕組みを，Agent の補助ツールとして作りました．
ドキュメント同士の有向非巡回グラフを定義し，タスクの起点（ファイルパス）から純粋なアルゴリズムで確実にコンテキストをかき集める（Aegis ではこれをコンテキストのコンパイルと読んでいます）仕組みです．

技術的には，リポジトリ内のドキュメント群を SQLite で管理しており，データベース上でファイルとドキュメントの間にエッジ（依存関係）を定義しています．Agent が特定のパスにあるファイルを編集しようとしたら，そのパスにエッジで結ばれたドキュメント群を SQLite の再帰 CTE で辿って返します．ドキュメント間にもエッジが貼ってあるので，「A を返すなら B も必要」という推移的な依存も解決できます．RAG と違い，検索はせず，ランキングも計算しないので，同じ入力には常に同じ出力が返ります．

# 使いながら知識を育てる Observation サイクル

Aegis は，導入時にリポジトリ内のドキュメントをインポートしますが．取り込まれるドキュメントは最初から完璧である必要はありません．
使っていく中で Agent が不足を見つけ，知識ベースの改善を提案できるような仕組みが整っています．

このフィードバックループの中核が Observation（観察報告）です．

## Agent 自身がガイドラインの不足を報告する

Aegis をセットアップすると，Agent への指示（Cursor Rule や CLAUDE.md, AGENTS.md）に「コードを書いたあとにセルフレビューして，ガイドラインが足りなかったら `aegis_observe` を呼べ」というルールが自動で埋め込まれます．

例えば，Agent が `src/api/handlers/user.ts` を編集しようとして， `aegis_compile_context` を呼んだとします．
返されたガイドラインに従ってコードを書きましたが，レビューで「バリデーションは Zod を使え」と指摘されました．

このとき，Agent は自動で Observation を記録します

```
aegis_observe({
  event_type: "compile_miss",
  payload: {
    target_files: ["src/api/handlers/user.ts"],
    review_comment: "API ハンドラのバリデーション規約が不足していた"
  }
})
```

Aegis 自身が何かを検知するわけではありませんが，Agent にルールに沿ったセルフレビューを促し自己申告させるようヒントを与えます．
また， `aegis_observe` も MCP の１ツールなので，人間がレビューで気づいた段階で Agent に Observe させることも可能です．

## Observation から Proposal へ

記録された Observation は Aegis の自動分析パイプラインで処理されます．先ほど出てきた `compile_miss` なら「どのパスにどのドキュメントへのエッジが不足していたか」を分析し，「エッジ追加の Proposal」を自動生成します．

## 人間が承認して初めて知識が更新される

ここが重要です．Agent は Observation を報告できますが，知識ベースを直接変更する権限を持っているわけではありません．

Aegis は Agent Surface（読み取り専用４ツール）と Admin Surface（管理用 16 ツール）を完全に分離しています．
Proposal の確認・承認は Admin Surface で行います．具体的には，Admin 側の Agent に「溜まっている Proposal を見せて」と頼めば一覧を取得できるので，人間が内容を確認して承認/却下を行います．

```
日常の開発
  └→ エージェントがセルフレビューでガイドライン不足を発見
       └→ aegis_observe で報告（Observation）
            └→ 分析パイプラインが改善案を生成（Proposal）

定期的なメンテナンス（Admin surface）
  └→ 「Proposal を確認して」と依頼
       └→ 内容を確認 → 承認 or 却下
            └→ 承認された変更が次回のコンパイルから反映
```

つまり，使えば使うほど知識ベースは洗練されていきますが，その成長は常に人間がコントロールします．

# セットアップ

MCP 設定に agent と admin の２つのサーバーを追加し，Agent に「Aegis を初期化してアダプタールールをデプロイして」と頼むだけでセットアップが開始されます．
Cursor，ClaudeCode，Codex のいずれでも `npx @fuwasegu/aegis` で起動できます．

```json
{
  "mcpServers": {
    "aegis": {
      "command": "npx",
      "args": ["-y", "@fuwasegu/aegis", "--surface", "agent"]
    },
    "aegis-admin": {
      "command": "npx",
      "args": ["-y", "@fuwasegu/aegis", "--surface", "admin"]
    }
  }
}
```

初期化後，Admin surface でアーキテクチャドキュメントをインポートし，ファイルパスとの対応（エッジ）を設定すれば準備完了です．
以降，Agent がコードを書く前に自動で `aegis_compile_context` を呼び，対象ファイルに関連するガイドラインだけを受け取るようになります．さらに，そこには再現性があります．確率的ではなく決定的に，同じファイルの変更に対して同じガイドラインが取得されるというわけです．

# 実プロジェクトでの計測結果

Token 消費に関して，とある実験をしました．
僕が開発を担当している，17 モジュール，140 以上の UseCase を持つ Laravel プロジェクトで，同じ質問を ClaudeCode（Opus4.6）に投げて，その時の応答時間や消費 Token などを計測して比較しました．

> **質問**： 「UseCase を実装する上での注意点は？」


| | Aegis あり | Aegis なし |
|---|---|---|
| 応答時間 | **43 秒** | 2 分 32 秒 |
| Output Token | **1.8k** | 10.3k |
| ツール呼び出し | **約 6 回** | 55 回 |
| 探索の隠れコスト | なし | 65.4k tokens |

Aegis なしの場合，Agent はまず `find` や `grep` でプロジェクト全体を探索し， 30 以上のファイルを読み込み，パターンを再帰的に推測しました．
55 回のツール呼び出しで 65.4k Tokens を消費し，結果は「142 の UseCase がこういうパターンで実装されている」という事実の列挙になっていました．

Aegis ありの場合， `aegis_compile_context` が対象ファイルに関連するガイドライン（レイヤー設計，命名規則，CRUD 設計ガイドなど）をまとめて返しました．
Agent はそれを読んで回答するだけです．回答にはパターンだけではなくて，「なぜそうなっているのか」の設計意図まで含まれていました．
これはドキュメントにチームの意思決定記録（ADR）が含まれていて，それが正しく関連付けられコンパイルに含められたからです．
このような設計意図は，実装の分析からは取得できないため，Agent がドキュメントにたどり着く必要がありますが，Aegis を使うことで最短ルートでそれが実現していました．

トークン効率で約 12 倍，応答速度で 3.5 倍，そして回答の質は「パターンの列挙」から「設計意図を含む回答」に変わりました．

# まとめ

Cursor Rules や AGENTS.md, Agent Skills も大変有効なツールですが，リポジトリで管理するコンテキストが増えれば増えるほど，手動管理が大変になる上 Agent が正しく最小限の読み込みでドキュメントを取得するには，Aegis のようなツールが必要です．
